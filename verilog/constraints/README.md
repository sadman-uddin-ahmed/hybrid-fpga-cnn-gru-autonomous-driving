# FPGA Constraint Files

This directory contains the board-specific Xilinx Design Constraints used for the Basys-3 and Nexys Video FPGA implementations.

The repository retains both the earlier direct Basys-3 constraint configuration and the later common wrapper-based configuration used during the device-scalability and architecture-optimisation work.

## Directory Structure

```text
constraints/
├── README.md
│
├── basys3/
│   ├── cnn_feature_demo_top_baseline.xdc
│   └── cnn_feature_basys3.xdc
│
└── nexys_video/
    └── cnn_feature_nexys_video.xdc
```

## Current Optimized RTL Hierarchy

The current optimized RTL contains two relevant top-level modules:

```text
cnn_feature_nexys_video_top
        |
        v
cnn_feature_demo_top
        |
        v
CNN feature extractor
+
four-frame temporal buffer
```

Despite its historical filename, `cnn_feature_nexys_video_top.v` acts as the eight-LED board wrapper used by the current board-specific constraint files.

Its external interface is:

```text
clk
reset_button
start_button
led[7:0]
```

Internally, it instantiates:

```text
cnn_feature_demo_top
```

using the instance name:

```text
cnn_feature_demo_top_inst
```

The wrapper maps the internal status signals as follows:

```text
led[0] = Done
led[1] = Busy
led[2] = Started
led[3] = Pass
led[4] = Fail
led[5] = Status/debug bit 0
led[6] = Status/debug bit 1
led[7] = Status/debug bit 2
```

## Current Basys-3 Constraint File

Use:

```text
basys3/cnn_feature_basys3.xdc
```

with the current wrapper-based implementation.

The constraint file expects the top-level ports:

```text
clk
reset_button
start_button
led[7:0]
```

and constrains the generated 50 MHz CNN core clock through:

```text
cnn_feature_demo_top_inst/cnn_core_clk_buf/O
```

This hierarchy corresponds to `cnn_feature_demo_top` being instantiated inside the wrapper.

The Basys-3 board clock remains:

```text
100 MHz external clock
```

and the CNN core clock remains:

```text
50 MHz
```

through divide-by-two clock generation.

## Current Nexys Video Constraint File

Use:

```text
nexys_video/cnn_feature_nexys_video.xdc
```

with the same wrapper-based RTL hierarchy.

This file also expects:

```text
clk
reset_button
start_button
led[7:0]
```

and uses the same internal generated-clock hierarchy:

```text
cnn_feature_demo_top_inst/cnn_core_clk_buf/O
```

The main difference from the Basys-3 XDC is the physical package-pin and I/O-standard mapping required by the Nexys Video board.

## Baseline Basys-3 Constraint File

The earlier Basys-3 implementation is retained as:

```text
basys3/cnn_feature_demo_top_baseline.xdc
```

This file is paired directly with:

```text
cnn_feature_demo_top
```

rather than the later eight-LED wrapper.

Its top-level status signals are therefore exposed separately:

```text
led_done
led_busy
led_started
led_pass
led_fail
led_status[4:0]
```

Its generated CNN-core clock constraint directly targets:

```text
cnn_core_clk_buf/O
```

because the BUFG exists directly inside the selected top module rather than beneath a wrapper instance.

## Historical Naming Note

The module name:

```text
cnn_feature_nexys_video_top
```

originated during the Nexys Video porting stage.

The wrapper itself primarily provides a common:

```text
clk
reset_button
start_button
led[7:0]
```

board-facing interface around the validated `cnn_feature_demo_top` architecture.

For the later optimized implementation, the same wrapper interface is compatible with both current board-specific XDC files.

The historical module name has been retained to avoid unnecessary modification of validated RTL and to preserve traceability to the implementation used during the dissertation experiments.

## Timing Constraints

Both current board-specific XDC files define:

```text
External board clock = 100 MHz
CNN core clock       = 50 MHz
```

The CNN core clock is generated by divide-by-two logic followed by a BUFG.

The push-button inputs are treated as asynchronous human-operated controls and are synchronised internally.

LED outputs are status indicators rather than timing-critical synchronous external interfaces.

## Reproduction Note

When recreating a Vivado implementation, ensure that:

1. the selected RTL top module matches the interface expected by the chosen XDC file;
2. only the XDC for the target board/configuration is enabled;
3. all required RTL and `.mem` verification/parameter files are available;
4. the 100 MHz board clock and generated 50 MHz CNN clock constraints are recognised correctly before implementation.

The constraint files in this repository are preserved to document the validated dissertation implementations rather than to provide a board-agnostic automatic build system.
